# What "working" means — and what locks it

This file is the contract. Each row is a promise the extension makes, written in plain language,
next to the automated test that will FAIL the moment that promise breaks. `pnpm test` (244 tests)
runs them all; CI blocks any change that violates a promise. If you hit a behaviour that feels
broken and it is **not** on this list, that is a missing guarantee — it should become a new row +
test, not a one-off patch.

## The promises

| # | Promise (what you should always see) | Locked by test |
|---|--------------------------------------|----------------|
| 1 | **The most powerful model of a provider is always used, at the reasoning level your session runs at, including newly released Codex models.** Live per-account catalogs and server priority determine the flagship; failover switches the *account*, never quietly drops you to a weaker model. Extreme reasoning levels are never forced. | `high reasoning is the baseline and is restored across every provider rotation` · `live OpenAI catalog adds an unseen flagship to account aliases and failover selects it at high` · `live Codex catalog follows server priority: Sol beats Terra and Luna` · `unknown future Codex generations rank without an extension release` |
| 2 | **A downgraded turn is upgraded back to the flagship** as soon as it is available again. | `failover prefers the latest model: a turn stuck on gpt-5.4 is upgraded back to gpt-5.5 on a codex→codex switch` |
| 3 | **`/multi-account next` cycles through EVERY logged-in account** — it never collapses onto one provider, even when stale usage marks another account as cooling. | `manual next cycles through every account instead of ping-ponging between two` · `manual next keeps every account selectable and always at its flagship model` · `manual next reaches an account blocked only by stale usage while free providers remain` |
| 4 | **`/multi-account switch X` switches to X** even if X was left invalidated by an old, since-fixed problem — it revives and selects it. | `manual switch revives a stuck invalidation and selects the account` |
| 5 | **A maxed account is never hot-retried every second.** When usage can't see a session/rate limit, the real cooldown still sticks and the session waits. | `a session limit the usage window can't see is not hot-retried every second` |
| 6 | **A cooldown that was over-estimated is corrected** the moment real usage shows the window reset, credits were added, or the account changed plans — every rotation account is refreshed independently. | `a long over-estimated cooldown is corrected by fresh usage and resumes` · `background usage refresh discovers an early Codex reset or plan upgrade on every benched account` |
| 7 | **When every account is cooling, work waits and resumes on whichever recovers FIRST** — not in rotation order, not never. | `resume fires on whichever account recovers first, not rotation order` · `all-limited work resumes in the same live session after cooldown` |
| 8 | **A freshly re-logged / re-keyed account returns to rotation** automatically. | `re-login clears a persisted invalidation when the slot credential changes` · `/multi-account revive restores an invalidated account to rotation` |
| 9 | **A transient blip never permanently kills an account.** Only a truly dead credential is removed, and only after repeated proof. | `repeated 401s on the SAME unrefreshed token never permanently invalidate` · `a temporary forced-refresh failure cools the slot without permanently invalidating it` · `one final 401 is counted once, does not invalidate OAuth, and fails over` |
| 10 | **Auto-resume never dead-ends in a red error.** It works even on host builds without `pi.continueAgent`, and never crashes with "Agent is already processing". | `host build WITHOUT pi.continueAgent still auto-resumes the failover ...` · `an un-continuable resume ... recovers by injecting the continuation prompt — never a red error` |
| 11 | **A 100% usage forecast does not skip a same-family sibling that has not refused this session.** Automatic failover tries that sibling first (the exact model if the account has it, otherwise its flagship, at the session thinking level). A sibling that already 429'd this session is skipped. A spent account of a *different* family is still not landed on. | `a 100% usage forecast on a Codex sibling does not skip it for Claude` · `a spent account known ONLY from a STALE usage snapshot is still tried when it is a same-family sibling` · `a sibling that already refused yields to another family` · `a 100% usage forecast still benches a dead account when failing over FROM another family` |
| 12 | **A far-future / bogus cooldown never evicts a live account for weeks.** | `a persisted far-future cooldown is clamped to the live ceiling on load` |
| 13 | **A stuck/silent resumed turn self-heals** — the watchdog cancels it and re-arms resume, but never interrupts a running build/test. | `a silent resumed turn is AUTO-cancelled and auto-resume armed ...` · `the watchdog never aborts a resumed turn while a tool (build/test) is running` |
| 14 | **Repeated failures open a breaker** and drop to manual mode instead of looping forever. | `after repeated resume failures the breaker opens and auto-continue stops (advisory mode)` |
| 15 | **Each provider gets requests in a shape it accepts.** Qwen/Alibaba never receives the OpenAI-only `developer` role (it is rewritten to `system`); OpenAI/Codex keeps it. | `Qwen requests rewrite the OpenAI-only 'developer' role to 'system'` |
| 16 | **Every provider shows the most useful status it can.** Qwen (no quota API) shows live available / rate-limited / needs-login; Ollama shows plan + renewal date + suspended; Codex/Claude show real % windows. | `Qwen shows live availability / rate-limit status (it has no quota API)` · `Ollama /api/me surfaces plan tier, renewal date, and suspended status` |
| 17 | **The quota footer does not blank out on OAuth token rotation** — it shows the last known usage rather than nothing, and a theme error can never wipe it. | `usage footer survives an OAuth token rotation instead of blanking` |
| 18 | **The extension loads on every supported install layout and every supported pi-ai.** A hoisted `npm install`, a git checkout, or a pi-ai that moved its OAuth API (0.80+) must never produce "Failed to load extension". If OAuth truly cannot be adapted, subscription login degrades with a clear message while API-key accounts keep rotating. | `pi-ai is discovered when hoisted next to the package, not nested inside it` · `hoisted install with a pre-0.80 pi-ai: extension loads and OAuth works` · `hoisted install with pi-ai >= 0.80 (types-only dist/oauth.js): extension loads and OAuth is adapted` · `no pi-ai at all: the extension still loads instead of dying at startup` |
| 19 | **A brand-new model generation works without waiting for a release of this extension** — for OpenAI *and* Anthropic. Whatever the host Pi (or the live per-account catalog) knows about is ranked and selectable, on numbered account aliases too, not just the base provider. | `a Codex generation only the HOST knows about (gpt-5.6) wins without a release: no silent fallback to gpt-5.5` · `an unreleased Codex generation is also selectable on a numbered account alias, not just the base provider` · `a newly released Claude flagship outranks the newest one this extension shipped with` · `an unreleased future Claude generation ranks without an extension release` · `Claude ordering is tier-first, then generation` |
| 20 | **Optional providers stay invisible until you install them.** With Cursor support enabled by default but the Cursor provider not cloned, no `cursor-account-*` login slot is offered and no startup warning appears; asking for it explicitly (`/multi-account add cursor`) is what surfaces the install instructions. | `includeCursor default-on never registers a phantom cursor slot nor warns while the Cursor provider is not installed` · `cloning the Cursor provider is enough: the spare cursor slot appears on the next rediscover` · `add cursor guides the user through subscription login, not API-key setup` · `no Cursor provider installed stays completely silent` |
| 21 | **An optional provider that is installed but broken cannot damage anything else.** A Cursor clone incompatible with your Node version never escapes as an unhandled rejection, never aborts session start, and never lets a previous session's paused work leak into a new one. It is reported once and everything else keeps working. | `a Cursor provider that fails to load cannot abort session_start` · `a Cursor provider that fails to load never escapes as an unhandled rejection` · `a Cursor provider that fails to load is reported once, not silently swallowed` |
| 22 | **Your thinking level is yours.** The extension never overrides it: a delegated agent configured `--thinking low` stays `low`, a mid-session `/thinking` change wins on the next turn, and a weaker fallback model's clamp is restored (never adopted) so the level cannot ratchet downward. Setting `reasoningLevel` explicitly still forces a level for people who want that. | `a per-agent thinking level (--thinking low) is never clobbered to the global default` · `a weaker fallback model's clamp never ratchets the thinking level down` · `a mid-session /thinking change is honoured on the next turn and across failover` · `an explicit reasoningLevel in config still forces that level on every turn` |
| 23 | **Maintenance automation lands or shouts — it never fails quietly.** The weekly `CLAUDE_CODE_VERSION` check (the constant inside the Anthropic OAuth billing header) pushes the bump to `main` itself instead of asking GitHub Actions to open a PR it is not permitted to open, opens an issue if that push is refused, and sweeps up any orphan `chore/claude-code-version-*` branch. Renaming or reformatting the constant breaks CI, not a silent Monday cron. | `the version-check workflow can still find the constant it is supposed to edit` · `the workflow's sed actually rewrites the constant` · `the bumped constant is the one that ships in the OAuth billing header` · `the version check never again depends on GitHub Actions opening a pull request` |

| 24 | **The work in flight when an account died is still there after the switch.** The turn that triggered the failover is rewritten into a verbatim handoff record — reasoning, output, every tool call and its result, with the calls that never returned flagged as unknown — instead of being dropped by pi-ai as an unreplayable turn. The record renders identically on every request (so it never moves the prompt-cache breakpoint) and is hard-capped (so it cannot blow the new account's context window). | `REAL pi-ai transform erases the interrupted turn; preservation carries it across a provider switch` · `the turn that triggered the failover survives into the account that takes over` · `the handoff record marks which tool calls never returned` · `preservation is byte-identical on replay so it never invalidates the prompt cache` · `oversized turns are clipped head+tail so failover can never blow the context window` · `every interrupted turn in a long session is preserved, not just the last one` · `preserveInterruptedContext: false restores the old drop-everything behaviour` |

| 25 | **Work resumes by itself even when nothing rotated.** A transient overload or an expired cooldown that returns to the SAME account auto-continues on hosts without `pi.continueAgent` — it does not stall waiting for you to re-send. When a continuation genuinely cannot be dispatched, the debug log names the actual reason instead of blaming the Pi build. | `a same-account pending resume auto-continues on a host without pi.continueAgent` · `a blocked continuation records why, instead of failing silently` · `transient overload retries the same account instead of rotating siblings` |

| 26 | **A provider's forecast never parks an account.** Reset timestamps and used-percentages are predictions — providers refresh quota windows early and unannounced, and resize the windows themselves — so no cooldown, reset time or usage reading keeps an account from being tried again for longer than `maxRecheckIntervalMs` (default 10 min). Forecasts still order the queue: an account nothing predicts as spent is tried first, and among equals the one that refused longest ago wins. | `a month-long quota forecast cannot park an account past the recheck ceiling` · `once the recheck ceiling elapses, an untried account still outranks one that refused` · `a 100% usage forecast still benches a dead account when failing over FROM another family` · `a genuinely maxed monthly Codex account is benched for its REAL reset ...` |

| 27 | **Every thinking level a model advertises is available — and none that it doesn't.** `max` is offered on models that advertise it (GPT-5.6 Sol/Terra/Luna do) and accepted as an explicit `reasoningLevel`, restored after a switch like any other level. The known-levels list is a filter, never a grant: provider gradations differ wildly and do not nest, so what a model gets comes from its own advertised efforts. | `a model that advertises max gets max — and one that does not, does not` · `reasoningLevel: max is honoured instead of being silently dropped to auto` · `max survives a switch through a weaker model, exactly like every other level` |

| 28 | **An exhausted account first fails over to a sibling with the same model and thinking level** — not to a random flagship of another family. A 100% usage forecast is not a refusal: that sibling is tried once, pinned through both preflights of the continuation. Only when no sibling can take the model, or every sibling has already refused this session, does rotation leave the family. Effort-folded Cursor ids (`cursor-grok-4.6-high` ≈ `cursor-grok-4.6`) count as the same model. Same-family flagship upgrades (gpt-5.4 → gpt-5.5) still happen. | `exhausted account fails over to a sibling with the same model before any other family` · `a 100% usage forecast on a Codex sibling does not skip it for Claude` · `a sibling that already refused yields to another family` · `cursor failover keeps grok and thinking level instead of jumping to another family` · `cursor-grok-4.6-high on one account matches folded grok on a sibling` · `failover prefers the latest model: a turn stuck on gpt-5.4 is upgraded back to gpt-5.5 on a codex→codex switch` |
| 29 | **Compaction never leaves "Compacting context…" spinning forever.** A spent account's summary is generated on a live account; a healthy current account is compacted with the same time bound, not Pi's untimed default; a timed-out attempt is aborted (not leaked) and the next live account is tried; if none can finish, compaction is cancelled so the spinner stops. Pi's default is never given a spent account. | `session_before_compact: a timed-out live summary is aborted and cancelled — never handed to the spent account` · `session_before_compact: a healthy current account is compacted with a time bound, not Pi's untimed default` · `session_before_compact: a timed-out compact on the current healthy account is aborted and the next live account is tried` · `session_before_compact: cancels instead of hanging on Pi default when no account is available` · `session_before_compact: Escape cancels immediately instead of starting Pi default on the spent account` · `session_before_compact: a timeout on the first live account tries the next one` · `session_before_compact: returns the summary from a live account` |

| 30 | **Cursor turns report real prompt usage, including tool-call pauses.** Auto-compact and the footer must see the request size even when Cursor omits `tokenDetails`. | `Cursor prompt tokens are estimated from the request when the stream reports none` · `Cursor tokenDetails still win over the request estimate` · `a tool-call turn with no tokenDetails is not reported as empty usage` |
| 31 | **Anthropic's third-party extra-usage 400 fails over as a limit**, not as a malformed request. | `Anthropic third-party extra-usage 400 is a limit, not a request bug` |
| 32 | **Ollama Cloud's live catalog is discovered, so new Cloud models appear in `/model` without editing `models.json`.** `https://ollama.com/v1/models` is fetched at startup and on idle sweeps; canonical bare ids (`kimi-k3`, `glm-5.2`) are merged with the built-in and configured lists for the base provider and every cloned slot. A failed fetch leaves the previous list intact. | `fetchOllamaCloudCatalog parses the /v1/models data array into canonical ids` · `fetchOllamaCloudCatalog throws on HTTP error` · `fetchOllamaCloudCatalog throws on empty catalog` |
| 33 | **Cursor `resource_exhausted` (gRPC quota) fails over as a limit**, so a dead Cursor account stops killing every turn with `Provider finish_reason: error`. | `Cursor resource_exhausted (gRPC quota) is a limit, so failover moves off the spent account` |
| 34 | **A live catalog sync is not lost when `only-active` is on.** Hidden providers keep a fresh copy of their models, so `/multi-account switch` right after startup still shows the newly discovered ids (`kimi-k3`, …) instead of the old pre-sync list. | `a catalog sync refreshes the only-active hidden copy, so an immediate switch shows fresh models` |
| 30 | **A forced OAuth refresh either lands or is never attempted.** Providers that rotate refresh tokens (Anthropic, Cursor) revoke the old token the moment a new one is issued, so an unpersistable refresh destroys the account. The ability to store the result is checked BEFORE the network call, and the result is written through pi's locked `modify()`, older hosts' `set()`, or `auth.json` directly — never dropped. A refresh that cannot be stored is reported as terminal, not as a success. | `a refreshed credential is persisted through pi 0.84's AuthStorage, which has no set()` · `with nowhere to persist, the token is never rotated in the first place` · `persistence falls through modify -> set -> auth.json instead of dropping the token` · `a forced Cursor refresh loads the vendored provider, not the retired clone path` |
| 31 | **Pi's model registry is Pi's, not ours.** This extension may unregister only the rotation slots it invented (`*-account-N`); a provider Pi knows on its own — built-in, `models.json`, another extension — is never emptied to narrow `/model`, because the registry is where everything resolves a pinned model by reference and a missing entry silently demotes that caller to the rotating session model. Anything published into `models.json` is published usable: resolvable AND authenticable by a bare `pi -p` child, or not published at all. | `only-active never makes a model Pi knows on its own unresolvable` · `only-active empties this extension's own slots and nothing else, ever` · `failover under only-active unhides the target before switching and re-narrows after` · `a slot published into models.json is usable by a bare child, not just resolvable` · `the published placeholder is the one the vendored proxy actually accepts` |

| 35 | **A child launched by `pi-subagents` runs on the exact provider/model/thinking candidate its parent selected.** `PI_SUBAGENT_CHILD=1` makes this extension passive as a router: it does not restore or persist remembered models, preflight-switch, rewrite interrupted context, queue input, route compaction, handle assistant errors, or auto-continue. Provider registration and request shaping remain available, while the original failure reaches the parent's verified `fallbackModels` chain unchanged. | `pi-subagents child keeps its explicit launch model and delegates fallback to the parent runner` |

## How to keep this honest

- **Every bug fix adds a row here and a test.** A fix without a locking test is not done.
- Run `pnpm test` before every release; the version in `index.ts` (`const VERSION`) and
  `package.json` must match and be bumped.
- When a promise here can't be expressed as a fast unit test, write the cheapest test that
  exercises the real code path (see `test/failover.test.ts` — it drives the real event handlers
  against a scripted host, not mocks).
